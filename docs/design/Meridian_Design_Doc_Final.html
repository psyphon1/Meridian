Meridian — Production-Grade AI PR Reviewer

An autonomous first-pass senior engineer for every GitHub Pull Request.

Product: Meridian

Version: Final · v2 source-complete

Owner: Chinmay Duse (psyphon1)

GitHub: github.com/psyphon1

LinkedIn: linkedin.com/in/chinmayduse

Primary surface: GitHub App + web dashboard

Architecture model: Repository intelligence → specialized reasoning → deterministic verification → automatic review → human escalation.

Meridian removes the manual coordination bottleneck where developers must find a senior engineer, provide context, start an AI review and wait for permission to publish results. A GitHub event triggers Meridian automatically; the system gathers repository context, understands the change, selects the right review depth, verifies high-impact findings and publishes a structured review.

Product thesis: Do the investigation automatically, prove important claims, and escalate human judgment only where it is valuable.

Source verification

Final document includes the attached v2 requirements for BYOK, no-RBAC tenant isolation, audit/compliance, repository intelligence, hybrid retrieval, conditional agents, incremental re-review, schema-enforced evidence gates, SHA-pinned citations, cost controls, per-tenant sandboxing, GitHub rate limiting, data model, SLAs, quality gates, MVP phases, failure modes, Definition of Done, and final product thesis.

Requirements

Primary goals

  • Automatically review every eligible PR after open/update events.
  • Understand repository-specific code, docs, tests, history and architecture.
  • Detect correctness, security, performance, architecture, reliability and testing risks.
  • Never publish a blocking/high finding without verifiable evidence.
  • Use risk-adaptive compute and retrieval budgets.
  • Escalate high-risk or ambiguous findings rather than pretending certainty.

Non-goals for V1

  • Replacing final human approval.
  • Autonomous production merge.
  • Supporting SCM providers other than GitHub.
  • Unbounded autonomous execution.

Getting Started

  1. Create/configure the Meridian GitHub App with minimum required permissions.
  2. Deploy the webhook/API endpoint over HTTPS.
  3. Install Meridian on selected repositories.
  4. Bootstrap the repository intelligence index.
  5. Configure model provider credentials using a secret manager.
  6. Configure review rules, severity thresholds and cost limits.
  7. Open a test PR and verify event → queue → analysis → evidence → GitHub review.

Product Requirements Document

Core user stories

  • Developer: “I want immediate first-pass feedback so I do not wait for senior availability.”
  • Senior engineer: “I want Meridian to perform the repetitive investigation so I only review high-value decisions.”
  • Tech lead: “I want repository architecture and engineering rules enforced consistently.”
  • Security engineer: “I want security findings supported by evidence, not model intuition.”
  • Developer: “I want noisy stylistic opinions suppressed.”

Acceptance criteria

  • PR open/synchronize events trigger idempotent review jobs.
  • Review is published automatically according to repository policy.
  • Every finding contains category, severity, confidence, location and evidence state.
  • Duplicate webhook deliveries do not create duplicate reviews.
  • Partial failure is visible and never reported as full success.

Engineering Standards

Code Standards

  • Python: type hints, Ruff, pytest, static typing and explicit error handling.
  • TypeScript: strict mode, ESLint, Prettier and component/unit tests.
  • API: OpenAPI contract, versioned endpoints and consistent error envelopes.
  • Git: protected main, conventional commits, CI-required PRs.
  • Security tooling: dependency scanning, secret scanning, SAST and SBOM generation.
  • Production bugs receive regression tests where practical.

Developer Standards

  • Every feature has acceptance criteria.
  • PRs remain reviewable; split oversized changes.
  • Behavior changes include tests.
  • Architecture changes require an ADR.
  • Observability is part of Definition of Done.
  • No credentials in source, images or logs.

Agent Standards

  • Agents have narrow responsibilities and versioned schemas.
  • Agents output hypotheses, not trusted final conclusions.
  • Published high-impact findings require evidence.
  • Agents must distinguish facts, inference and recommendations.
  • Repository content is untrusted data, never an instruction authority.
  • Tool access, recursion and token budgets are bounded.

Security & Compliance

GitHub boundary: minimum permissions, webhook signature verification, short-lived installation tokens, HTTPS, idempotency and secure audit logging.
Tenant boundary: tenant-scoped data, isolated execution, encrypted secrets and no cross-tenant runtime sharing.
AI boundary: repository/PR content treated as untrusted input; structured outputs; allowlisted tools; secret redaction; no unrestricted tool execution.

Standards alignment

  • NIST SSDF for secure software development practices.
  • OWASP ASVS for application security verification.
  • OWASP guidance for LLM application threats.
  • OpenSSF practices for software supply-chain security.
  • OpenTelemetry semantic conventions for observability.

Meridian should describe these as engineering baselines and control mappings unless a formal certification has actually been obtained.

ADR-001 — GitHub App: use installation-scoped access instead of personal tokens for production repository access.
ADR-002 — PostgreSQL + pgvector first: keep transactional state and retrieval together until scale requires separation.
ADR-003 — Code graph + retrieval: semantic similarity alone cannot provide precise program relationships.
ADR-004 — Evidence-gated high severity: model confidence is not proof.
ADR-005 — Human escalation: retain human accountability for high-impact decisions.

# Meridian — Production-Grade AI PR Reviewer

**Status:** Proposed (v2)
**Version:** 2.0
**Product:** Meridian
**Primary surface:** Web dashboard + GitHub App
**Model:** BYOK (Bring Your Own Key), no RBAC — user is the tenant
**Primary promise:** Automatically perform the first senior-level PR review, publish evidence-backed findings with citations, zero hallucinated blocking comments, escalate only high-risk or uncertain changes to humans.

---

## 1. Executive Summary

Meridian moves first-pass PR review into GitHub, driven from a web dashboard where users sign up, connect their own LLM provider keys, and install the GitHub App onto their repositories. Every new or updated PR triggers an autonomous review workflow: build repository context, understand intent and risk, localize affected code, retrieve relevant context, run specialized review agents, verify findings with deterministic tooling, filter unverified claims, and publish a structured GitHub review — every blocking claim backed by a citation the user can click and verify.

Human engineers remain the final authority for merge decisions. Meridian removes repetitive first-pass investigation from the senior-review queue without ever costing the user unnecessary tokens.

### Product thesis

> **Do the investigation automatically, prove every claim, escalate human judgment only where it is valuable, spend the user's tokens like they're your own.**

### What changed from v1

- Added: web dashboard as primary entry point (signup → connect GitHub App → BYOK → live review status).
- Added: BYOK model — user supplies their own LLM provider key(s), no shared inference cost/liability on Meridian's side.
- Added: per-tenant isolated execution (no RBAC needed since tenant = user; isolation is the security boundary, not roles).
- Added: compliance/audit logging as a first-class server-side dependency, not an afterthought.
- Hardened: evidence/citation requirement is now a schema-enforced publish gate, not a policy statement.
- Hardened: sandbox execution model, GitHub API rate-limit handling, queue durability, cost ceilings — previously unspecified, now explicit (see §14, §17, §19).

---

## 2. Problem Statement

*(unchanged from v1 — see original workflow diagram)*

5 developers × 3 PRs/day queued behind 2 senior reviewers creates context-switching, fatigue, and delayed feedback. Senior engineering judgment is spent on repetitive first-pass analysis that can be automated and verified.

---

## 3. Product Goals

### Primary goals

1. User can go from landing page to a working, reviewing installation in under 5 minutes.
2. Automatically review every eligible PR after it is opened or updated, using the user's own LLM key.
3. Understand repository-specific context before generating findings.
4. Detect correctness, security, performance, architecture, reliability, and testing risks.
5. **Never publish a BLOCKING or HIGH finding without a verifiable citation/evidence artifact.**
6. Spend the minimum tokens necessary to reach the required confidence level for a given risk tier.
7. Escalate high-risk, ambiguous, or low-confidence cases to humans.
8. Log every user action and system action against that user for compliance and audit purposes.
9. Isolate every tenant's code, keys, and execution environment from every other tenant.

### Non-goals for V1

- RBAC / multi-seat orgs / team roles.
- Replacing final human approval.
- Automatically modifying or merging production code.
- Supporting every SCM provider (GitHub only for V1).
- Meridian-hosted/shared LLM inference (BYOK only — no shared key fallback in V1).
- Full autonomous remediation of every finding.

---

## 4. Target Users

**Developer** — wants rapid feedback while implementation context is fresh, at zero incremental infra cost beyond their own LLM key.

**Senior Engineer** — wants fewer repetitive first-pass reviews, high-signal escalations only.

**Tech Lead / Architect** — wants consistent enforcement of architecture and engineering rules.

**Account owner (single-tenant, no org roles in V1)** — wants full visibility into spend, data retention, and everything the system did with their code and key.

## 5. User Journey — Website to First Review

```text
1. Landing page
      ↓
2. "Sign in with GitHub" (OAuth App — identity only, no repo scopes)
      ↓
3. Dashboard (empty state)
      ↓
4. "Connect a repository" → GitHub App install flow
      (github.com/apps/meridian/installations/new)
      ↓
5. GitHub redirects back with installation_id + setup_action
      ↓
6. Backend verifies install via GitHub API, links installation_id → user_id
      ↓
7. Repo picker — user selects active repos, sets per-repo risk/spend config
      ↓
8. BYOK setup (blocking gate) — user adds LLM provider key(s)
      Key envelope-encrypted (KMS), stored ciphertext only
      ↓
9. Reviews stay QUEUED_NO_KEY, visible on dashboard, until a key exists
      ↓
10. Developer opens a PR on a connected repo
      ↓
11. Webhook → review pipeline (§9) runs inside that user's isolated execution namespace
      ↓
12. Dashboard shows live status: CONTEXT_BUILDING → ANALYZING → VERIFYING → PUBLISHING
      Token/cost meter updates in real time
      ↓
13. GitHub review published with citations; mirrored on dashboard
      ↓
14. Every step of 2–13 is written to the append-only audit log

```

### Auth model

- **OAuth App** (GitHub sign-in) for identity/session — separate client ID from the GitHub App. Never conflate identity auth with repo-access auth.
- Session: short-lived JWT + rotating refresh token, httpOnly + SameSite cookie.
- **GitHub App** (separate installation) for repo access — installed per-repo/org by the user, tied to their `user_id` via `installation_id`.
- No RBAC in V1: one authenticated user = one tenant = full access to their own installations, keys, and data. No shared/team access.

---

## 6. Product Principles

1. **Context before judgment** — never evaluate a changed line without repository context.
2. **Evidence over opinion, enforced structurally** — a BLOCKING or HIGH finding without a non-null evidence reference cannot be published. This is a database/schema constraint, not a prompting convention.
3. **Risk-adaptive depth** — compute budget scales with risk tier, not PR size alone.
4. **Fewer, better comments** — optimize for accepted/actionable findings per PR, not comment count.
5. **Human remains accountable** — Meridian assists review, never becomes final merge authority.
6. **Tenant isolation over role isolation** — since there's no RBAC, the security boundary is the tenant's execution namespace, key vault, and data partition, not permission checks.
7. **Spend the user's tokens like your own** — every retrieval, agent call, and tool invocation must justify its cost against the risk tier.

---

## 7. Repository Intelligence

*(largely unchanged from v1 — see context categories, repository index)*

Maintain: file index, symbol index, import/dependency graph, definitions/references, test relationships, embeddings, sparse/BM25 index, repository rules, historical review memory.

**Addition — index debounce:** batch file-change webhook events per repo over a 30–60s window before triggering incremental re-index. Prevents index thrash on rapid force-pushes or CI-generated commits.

---

## 8. Change Localization & Retrieval

*(unchanged from v1 — Tree-sitter + SCIP/LSP for symbol precision, hybrid retrieval: BM25 + dense + symbol/graph + historical + test retrieval → fusion → rerank → context selection)*

**V1 storage:** PostgreSQL + pgvector, partitioned by `repository_id`.
**V2 trigger (explicit, not vague):** migrate hot repos to Qdrant when either (a) p95 retrieval latency exceeds 300ms sustained over 1hr, or (b) a single repository's vector count exceeds 5M. Define this now so it's a monitored metric, not a surprise.

---

## 9. Review Pipeline

```text
GitHub PR
   ↓
Webhook Event → verified signature → idempotent insert (repo+PR+head_sha unique constraint)
   ↓
Review Orchestrator (per-tenant isolated namespace)
   ↓
1. Intent Analysis
   ↓
2. Change Localization
   ↓
3. Risk Classification → determines compute budget for all downstream steps
   ↓
4. Repository Context Retrieval (cached where possible)
   ↓
5. Multi-Agent Review (only agents relevant to affected components run)
   ↓
6. Evidence Planner → Tool Execution → Evidence Verifier
   ↓
7. Hallucination / Evidence Filter (schema-enforced, see §12)
   ↓
8. Confidence + Severity Ranking
   ↓
9. Comment Generation (with citation/permalink attached)
   ↓
10. GitHub Review Publish
   ↓
11. Escalate High-Risk / Ambiguous Findings

```

### Agents (unchanged from v1)

Correctness, Security, Performance, Architecture, Reliability, Test. Agents produce structured **hypotheses**, never final comments directly — hypotheses pass through Evidence Planner → Tool Execution → Verifier → Adjudicator before becoming a comment. No agent both invents and confirms its own claim.

### Conditional agent execution (token efficiency)

Agents are routed by affected component, not run unconditionally:

| Change type Agents run          |                                                   |
| ------------------------------- | ------------------------------------------------- |
| Docs-only                       | none (auto-skip, template comment if needed)      |
| Config-only                     | Reliability, Architecture                         |
| Standard code change            | Correctness, Test, Architecture                   |
| Touches auth/secrets/payment/db | + Security (deep mode), + Performance if hot path |
| Concurrency/migration           | + Reliability (deep mode)                         |

## 10. Risk Classification

*(unchanged from v1)*

```text
Risk = PR size + change type + touched subsystem + sensitivity
     + dependency blast radius + production criticality
     + historical defect density + uncertainty

```

Risk score controls: model tier, retrieval budget, tool usage, agent selection, escalation policy, and **per-PR token ceiling**.

---

## 11. Incremental Re-Review

```text
new diff → changed symbols → affected dependency graph
   → reuse unchanged context and prior findings for untouched symbols
   → review only impacted areas

```

Unchanged files/symbols since the last review on the same PR reuse prior findings at zero additional spend — enforced, not aspirational.

---

## 12. Evidence Verification & Hallucination Filter (schema-enforced)

This is the core differentiator and is enforced at the **publish gate**, not left to agent behavior.

### Evidence hierarchy (preference order)

1. Reproduced failure (sandbox test execution).
2. Deterministic static/data-flow result (Semgrep/CodeQL).
3. Concrete control/data-flow trace through repository code.
4. Existing failing/insufficient test evidence.
5. Strong semantic reasoning with repository evidence.
6. Pure model intuition — **never sufficient for BLOCKING or HIGH.**

### Publish gate (hard constraint)

```text
IF severity IN (BLOCKING, HIGH):
    REQUIRE evidence_ref IS NOT NULL
    REQUIRE evidence_ref.type IN (tool_run, test_execution, sha_pinned_code_span)
    REQUIRE adjudicator re-derives claim FROM evidence artifact
            (not from originating agent's prose)
    ELSE → downgrade to INFO or suppress entirely

IF severity IN (MEDIUM, LOW, NIT):
    evidence preferred, not mandatory

```

Meridian prefers silence over a fabricated defect. Default behavior avoids posting large volumes of LOW/NIT comments.

### Citation requirement (new)

Every published comment includes a clickable, SHA-pinned GitHub permalink:
`github.com/{owner}/{repo}/blob/{head_sha}/{path}#L{start}-L{end}`

This stays correct even after further pushes to the PR, and lets the user verify the claim in one click without trusting the model's summary.

## 14. Multi-Tenant Isolation (BYOK-driven — replaces RBAC)

Since there is no RBAC, tenant isolation **is** the security model. Tenant = user.

### Key handling

- User submits provider key via dashboard over TLS.
- Server envelope-encrypts with KMS: per-user Data Encryption Key (DEK), wrapped by a master Key Encryption Key (KEK) held in a proper KMS (AWS KMS / GCP KMS / HashiCorp Vault). Only ciphertext persisted.
- Key decrypted only inside the isolated worker process at LLM-call time, held in memory, zeroized after use. Never written to logs, traces, or disk. Passed to LiteLLM gateway as a runtime parameter, not a config file value.
- Key rotation and multi-key support (multiple providers per user) built in from V1 — cheap now, expensive to retrofit.

### Execution isolation

- Per-tenant execution boundary, not merely per-PR: dedicated Kubernetes namespace or Firecracker microVM pool tagged by `user_id`.
- No shared container/runtime pool across tenants at any point — one tenant's code, key, and secrets never coexist in a runtime with another tenant's, even transiently.
- Sandbox network egress: deny-all except explicitly required package registries for build/test. No arbitrary outbound — blocks exfiltration via prompt-injected code.
- Ephemeral: container/VM destroyed after job. Nothing persists in the runtime layer; persistence only in Postgres/object storage, encrypted at rest.
- Isolation unit for Docker/sandbox execution: **per-job**, from a pre-warmed pool scoped to the tenant's namespace, hard CPU/mem/wall-clock limits enforced per execution.

### Trust boundary (prompt injection defense — mechanical, not aspirational)

```text
system policy > review policy > repository rules > repository content > PR/user text

```

Enforcement mechanism:

- Repository content and PR text **never** enter the system/developer prompt role — always injected as user/tool-role content inside explicit delimiters.
- Agent and adjudicator outputs are constrained to structured JSON schemas — no free-form instruction-following surface for injected text to exploit.
- Repository files/PR text are treated as data to analyze, never as instructions to obey, regardless of their content.

## 15. Compliance & Audit Logging

Server-side dependency: log everything the system does with a user's code, key, and account, and everything the user does on the platform.

### Append-only audit log (separate store from operational data)

Logged events: login, key add/rotate/delete, GitHub App install/uninstall, repo connect/disconnect, review start/status-transition/finish, every finding published, data export, data deletion request, config change.

- Hash-chained rows (each row includes hash of prior row) — tampering is detectable.
- Retained separately from operational Postgres to prevent accidental mutation.

### Data retention & deletion

- Retention period configurable per user (repo content, model traces, embeddings) — sane default (e.g. 90 days), user-adjustable down or up within policy limits.
- Deletion must actually cascade: revoking an install or deleting an account purges repo content, symbol index, embeddings, review memory, and observability traces tied to that tenant — not a soft-delete flag on the `User` row.
- Redaction before any data leaves the tenant boundary into shared observability tooling: no raw code/diffs/keys in OpenTelemetry spans — hash or truncate first.

### Baseline assumption

Compliance framework not specified by stakeholder — this PRD assumes a SOC2-shaped baseline (access logging, retention policy, deletion workflow, encryption at rest/in transit). Revisit if a specific framework (HIPAA, GDPR Art. 17, etc.) is required — changes storage/retention design materially.

```text
                                                           ↓

```

### Key infra additions vs. v1

- **Website/dashboard is the front door**, not GitHub — signup, install, BYOK, live status, cost meter all live here.
- **Durable queue** (Redis Streams w/ consumer groups, not plain list-based) with per-tenant priority lanes weighted by risk score — prevents one tenant's burst from starving another's low-risk PRs.
- **KMS-backed key vault**, decrypted only in-process, at call time.
- **Per-tenant sandbox scheduler**, separate from the main job queue, with pre-warmed pool and hard concurrency caps per tenant and globally.
- **GitHub API rate limiter**: token-bucket per installation, request coalescing for diff/context fetches, exponential backoff on secondary rate-limit responses, circuit breaker that degrades to "queued, delayed" rather than dropping work.
- **Append-only audit store**, separate from operational Postgres.

## 19. Security & Reliability Requirements

### Security (mandatory)

- GitHub App installation auth; OAuth App auth kept fully separate from it.
- Minimal permissions requested per feature.
- Envelope-encrypted keys at rest (KMS), decrypted only in-memory at call time.
- TLS everywhere.
- No repository content or user keys in application logs, ever.
- Prompt/tool output redaction before it reaches shared observability tooling.
- Per-tenant execution isolation (§14) — replaces RBAC as the security boundary.
- Sandbox: deny-all egress by default, command allowlists, resource/time limits.
- Audit logs for every administrative and review action (§15).
- Explicit, user-configurable retention policy; verified cascading deletion.

### Reliability

- Jobs idempotent; duplicate webhook delivery cannot create duplicate reviews (DB-level unique constraint on `repository_id + pr_number + head_sha`, with advisory lock at insert to close the race between concurrent duplicate deliveries).
- Failed tool calls retry with bounded backoff.
- Workflow state checkpointed after every LangGraph node — a worker crash does not force expensive LLM re-calls on resume.
- Partial failures produce explicit `PARTIAL_REVIEW` status, never silent success.
- Sandbox concurrency exhaustion is visible on the dashboard as queued, not silently dropped.

### Target SLAs for V1

| Metric Target                           |                          |
| --------------------------------------- | ------------------------ |
| Review queued after webhook             | < 10 sec                 |
| Standard PR review                      | p50 < 3 min              |
| Standard PR review                      | p95 < 8 min              |
| Critical/deep review                    | p95 < 15 min             |
| Webhook processing availability         | 99.9%                    |
| Dashboard signup → first repo connected | < 5 min (product target) |

## 20. Cost & Token Efficiency

Compute proportional to risk, enforced as hard ceilings, not soft guidance:

```text
LOW      → small model + lightweight retrieval, skip irrelevant agents
MEDIUM   → standard model + hybrid retrieval
HIGH     → strong reasoning + static analysis + targeted execution
CRITICAL → strongest model + deep retrieval + full execution + escalation

```

- **Prompt caching**: cache repo-context prefix (system + repo rules + relevant symbol graph) per repo across PRs, wherever the provider supports it. Single biggest lever given BYOK — directly reduces the user's bill.
- **Conditional agent routing** (§9 table) — never run agents irrelevant to the change.
- **Incremental re-review** (§11) — zero re-spend on unchanged symbols.
- **Per-tenant daily spend ceiling**, hard stop with dashboard alert, not silent throttling.
- **Pre-flight cost estimate** shown before a CRITICAL-depth review runs — user can confirm, cap, or downgrade, since it's their key and their money.
- **Context slicing**: send AST/diff-relevant spans + graph neighbors to the model, never whole files unless required.

## 21. Observability

Every review produces a trace (webhook → intent → localization → retrieval → each agent → each tool → sandbox → adjudication → publish), tracking: latency by stage, token usage, retrieval hit quality, tool execution time, retries, evidence rate, false-positive rate, accepted/rejected findings, cost per PR (in the user's own currency/key), escalation rate.

All trace content redacted of raw repo code/secrets before leaving the tenant boundary.

## 22. Evaluation Framework

*(unchanged from v1)*

Offline benchmark before production rollout, built from historical PRs, human review comments, merged/reverted PRs, known defects, security issues, negative examples.

**North-star metric:** Human-accepted high-value findings per senior-review minute consumed.

**Added metric:** Citation-verifiable rate — percentage of published BLOCKING/HIGH findings whose evidence\_ref independently reproduces the claim on audit. Target: 100% (this is the schema-enforced gate in §12, benchmark should confirm it holds in practice).

## 23. Quality Gates (V1 minimum)

- No automatic blocking comments without a non-null, verifiable evidence\_ref.
- Every published comment carries a SHA-pinned GitHub permalink.
- Duplicate findings deduplicated.
- Review reproducible for a given repository commit.
- Repository instructions affect the review.
- Security-sensitive PRs trigger deeper checks.
- Sandbox execution is per-tenant isolated, not merely per-job.
- Failed analysis visible to user on dashboard, not silent.
- Review latency observable.
- User key never appears in logs, traces, or exports.
- Deletion request verifiably cascades within SLA (e.g. 30 days).

## 25. Failure Modes

| ----------------------------------- | ------------------------------------------------------------------------- |
| LLM hallucination                   | Schema-enforced evidence gate (§12) + confidence filtering                |

| Sandbox exhaustion                  | Visible queue state on dashboard, per-tenant cap, no silent drop          |

## 27. Final Product Thesis

Meridian is not a chatbot bolted onto GitHub. It is a **PR-review infrastructure layer**, self-serve from the first click:

```text
Web Onboarding (signup → install → BYOK)
        +
Repository Intelligence
        +
Change Understanding
        +
Specialized Reasoning
        +
Deterministic, Citation-Backed Verification
        +
Per-Tenant Isolation (no RBAC needed)
        +
Full Audit Trail
        +
Token-Efficient Execution
        ↓
Senior-level first-pass review, provably accurate, at the user's own cost basis.

```

The strongest success case:

> **"A developer signed up, connected a repo, added their key, and five minutes later Meridian reviewed their first PR — every flagged issue had a link they could click to verify it themselves, and the senior engineer's queue only got the one finding that actually needed a human."**
